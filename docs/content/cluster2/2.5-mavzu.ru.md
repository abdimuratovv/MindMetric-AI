Авторские задания. Ключи и разборы включены в эту преподавательскую копию; файл не публикуется целиком студенту во время проверок.

## От требования к входу и выходу

Чтобы превратить жизненное описание в вычислительную задачу, запишите цель, вход, выход, единицы и ограничения. Не скрывайте неопределённость кодом.

В учебном примере тарифа все цены и правила задаются в условии. Это не действующая цена реального сервиса и не финансовая рекомендация.

Например, для платы за просрочку в библиотеке уточняют целочисленность дней, льготный период и обработку отрицательного входа. Без согласования требований нельзя определить правильный выход.

### Разобранный пример

В учебном тарифе аренда стоит 7000 сумов за день, число полных дней — 3. Какова общая плата?

1. Вход: дневная цена и дни.
2. Плата = 7000 × 3.
3. Выход — 21000 сумов.

Ответ: 21000 сумов

### Практика — `case-contract-practice-1`

Что сначала нужно уточнить в требовании «найдите самый удобный маршрут»?

- a) Критерий удобства: время, цена или другое требование
- b) Цвет кнопки
- c) Объявить случайный маршрут самым удобным

Ключ: a

1. «Удобно» преобразуется в измеримый критерий.
2. Затем сравниваются варианты.

Типичная ошибка: Не закрывайте неясную цель догадкой.

Подсказка: На каком основании один из двух маршрутов предпочтительнее?

- a: Без критерия лучший результат неопределён.
- b: Это не задаёт критерий выбора маршрута.
- c: Это не проверяет требование пользователя.

### Практика — `case-contract-practice-2`

В учебном условии коробка стоит 9000 сумов, количество — 5, доплат нет. Итого?


Ключ: 45000

1. Цена умножается на количество.
2. 9000 × 5 = 45000.

Типичная ошибка: Не добавляйте комиссию или скидку, которых нет в условии.

Подсказка: Используйте только заданные правила.


### Входная проверка — `case-contract-precheck`

Расстояние в км, скорость в км/час; выход — время в часах. Какая формула подходит? Скорость положительна.

- a) время = расстояние + скорость
- b) время = расстояние / скорость
- c) время = расстояние × скорость

Ключ: b

1. Время = путь / скорость.
2. Деление км на км/час даёт часы.

Типичная ошибка: Проверяйте формулу по единицам.

- a: Величины с разными единицами так не складываются.
- b: Единицы дают часы.
- c: Единицы не соответствуют времени.

### Итоговая проверка — `case-contract-postcheck`

Для суммы заказа введено отрицательное количество, а требуется положительное целое. Каков правильный выход?

- a) Без расчёта сообщить о необходимости исправить количество
- b) Показать отрицательную плату как готовый заказ
- c) Скрыто сделать количество положительным

Ключ: a

1. Количество нарушает требование.
2. Вместо расчёта выдаются состояние ошибки и путь исправления.

Типичная ошибка: Не заменяйте валидацию скрытым исправлением входа.

- a: Недопустимый вход обрабатывается по контракту.
- b: Это принимает недопустимый вход.
- c: Это несогласованно меняет введённые данные.

## Ограничения и недопустимый вход

Отдельно проверяются возможность прочитать текст как число, диапазон и единицы. «abc» — не число; отрицательное расстояние — число, но недопустимое в задаче.

Выполняйте проверку до вычисления. Возврат нуля при неверном входе мешает отличать ошибку от настоящего нулевого результата.

Сообщение должно указывать поле и способ исправления. Вместо персональных данных или внутренних технических деталей давайте нужную пользователю инструкцию.

### Разобранный пример

Число участников должно быть целым от 1 до 30. Что делать при вводе 0?

1. 0 ниже нижней границы.
2. Вычисление не начинается.
3. Выдаётся сообщение с допустимым интервалом.

Ответ: Вход отклоняется

### Практика — `case-validation-practice-1`

n — целое, 1 ≤ n ≤ 30. Какой вход допустим?

- a) 0
- b) 2.5
- c) 30

Ключ: c

1. Проверяются целочисленность и обе границы.
2. Только 30 выполняет все требования.

Типичная ошибка: Один диапазон не заменяет требование типа.

Подсказка: Требования должны выполняться совместно.

- a: Ниже нижней границы.
- b: Хотя в интервале, но не целое.
- c: Верхняя граница включена, число целое.

### Практика — `case-validation-practice-2`

В числовом поле введено «abc». Какое сообщение полезно?

- a) Результат: 0
- b) Введите положительное целое число в поле количества
- c) Ошибка!

Ключ: b

1. Вход не является числом.
2. Сообщение указывает нужное поле и допустимый формат.

Типичная ошибка: Не представляйте ошибку и вычисленный результат одинаково.

Подсказка: Пользователь должен понимать следующий шаг.

- a: Недопустимый вход показан как правильный результат.
- b: Понятны поле и способ исправления.
- c: Не указан путь исправления.

### Входная проверка — `case-validation-precheck`

Ограничение: 0 ≤ d ≤ 100. Какое значение недопустимо?

- a) −1
- b) 0
- c) 100

Ключ: a

1. Обе границы допустимы.
2. Отрицательное значение вне интервала.

Типичная ошибка: Не забывайте, что равенство включает границу.

- a: Ниже нижней границы.
- b: Нижняя граница включена.
- c: Верхняя граница включена.

### Итоговая проверка — `case-validation-postcheck`

Расчёт: total = price × quantity. Какой порядок подходит при недопустимом quantity?

- a) Вычисление → принятие → проверка
- b) Скрыть ошибку → показать total
- c) Проверка → сообщение → остановка расчёта

Ключ: c

1. Сначала проверяются требования к входу.
2. При недопустимости перехода к вычислению нет.

Типичная ошибка: Валидация — это и управление процессом, а не только сообщение.

- a: Проверка после принятия слишком поздняя.
- b: Это вводит пользователя в заблуждение.
- c: Результат не формируется из недопустимого входа.

## Модель ступенчатого тарифа такси

В учебной модели базовая плата b покрывает первые k километров. При d ≤ k плата b, при d > k — b + (d − k) × r. Здесь d — неотрицательное целое число километров.

Превышение границы считается отдельно. Повторная тарификация включённого расстояния приводит к двойному начислению.

Если ожидание, время или округление не заданы, не добавляйте их сами. Проверяйте границу тарифа и значения по обе стороны.

### Разобранный пример

b = 10000, k = 2, r = 3000; d = 5. Какова плата?

1. Превышение: 5 − 2 = 3.
2. Доплата: 3 × 3000 = 9000.
3. Итого: 10000 + 9000 = 19000.

Ответ: 19000

### Практика — `case-taxi-practice-1`

Учебный тариф: b = 12000, k = 3, r = 2000. Какова плата при d = 7?


Ключ: 20000

1. Превышение: 7 − 3 = 4.
2. 12000 + 4 × 2000 = 20000.

Типичная ошибка: Не умножайте всё расстояние на дополнительный тариф.

Подсказка: База уже покрывает начальное расстояние.


### Практика — `case-taxi-practice-2`

b = 12000, k = 3, r = 2000. Какова плата при d = 2?


Ключ: 12000

1. 2 ≤ 3, превышения нет.
2. Базовая плата остаётся 12000.

Типичная ошибка: Не начисляйте отрицательную доплату за расстояние меньше включённого.

Подсказка: Сначала определите ветвь для расстояния.


### Входная проверка — `case-taxi-precheck`

b = 9000, k = 2, r = 2500. Какова плата при d = 2?


Ключ: 9000

1. Сама граница входит в базу.
2. Доплаты нет, плата 9000.

Типичная ошибка: Не считайте расстояние на границе превышением.


### Итоговая проверка — `case-taxi-postcheck`

b = 15000, k = 4, r = 3000. При d = 6 найдите ДОПЛАТУ к базе.


Ключ: 6000

1. Превышение: 6 − 4 = 2.
2. Только доплата: 2 × 3000 = 6000.

Типичная ошибка: Не путайте общую плату и запрошенную доплату.


## Упрощённая модель банкомата

В учебной модели запрос снятия должен быть положительным, не превышать баланс и делиться без остатка на единственный доступный номинал. Комиссии и правила банков в модель не включены.

Условие принятия: (amount > 0) AND (amount ≤ balance) AND (amount mod note == 0). Только после выполнения всех условий новый баланс = balance − amount.

При отказе баланс не меняется. У реального банкомата есть запас купюр и другие ограничения; здесь задано достаточное количество купюр единственного номинала.

### Разобранный пример

balance = 100000, note = 10000, amount = 30000. Принят ли запрос и каков новый баланс?

1. Сумма положительна и не превышает баланс.
2. 30000 mod 10000 = 0.
3. Запрос принят, баланс 100000 − 30000 = 70000.

Ответ: Принят; 70000

### Практика — `case-atm-practice-1`

balance = 80000, note = 10000, amount = 50000. Каков новый баланс? Купюр достаточно.


Ключ: 30000

1. Все три условия выполнены.
2. 80000 − 50000 = 30000.

Типичная ошибка: После принятия вычтите снятую сумму.

Подсказка: Сначала проверьте условия принятия, затем баланс.


### Практика — `case-atm-practice-2`

balance = 100000, note = 20000, amount = 30000. Купюр достаточно. Каково решение?

- a) Принять: баланса достаточно
- b) Принять: запрос положителен
- c) Отказ: нет деления на номинал без остатка

Ключ: c

1. Запрос укладывается в баланс.
2. Но единственным номиналом точно выдать нельзя, баланс не меняется.

Типичная ошибка: Одной достаточности баланса недостаточно.

Подсказка: Вычислите остаток.

- a: Баланс — только одно условие.
- b: Положительность не отменяет другие требования.
- c: 30000 mod 20000 = 10000, условие не выполнено.

### Входная проверка — `case-atm-precheck`

balance = 40000, note = 10000, amount = 50000. Каков баланс после отклонённого запроса?


Ключ: 40000

1. Запрос больше баланса.
2. Он отклоняется, остаются прежние 40000.

Типичная ошибка: Не уменьшайте баланс до проверки.


### Итоговая проверка — `case-atm-postcheck`

balance = 60000, note = 10000, amount = 0. Каково решение?

- a) Отказ: запрос не положителен
- b) Принять: остаток нулевой
- c) Обнулить баланс

Ключ: a

1. Условие amount > 0 ложно.
2. Запрос отклонён, баланс не меняется.

Типичная ошибка: Не путайте свойство остатка нуля с положительностью.

- a: Даже делясь на номинал, ноль нарушает требование положительности.
- b: Одного условия недостаточно.
- c: Отказ или нулевой запрос не обнуляет баланс.

## Тестовые случаи и ожидаемый результат

В тестовом случае вместе с входом записывается ожидаемый выход. Одного слова «проверено» недостаточно для проверки правильности результата.

Для ветвей условия берите входы, ведущие по разным путям. Значения ниже границы тарифа, на ней и выше помогают выявлять ошибки.

Инвариант — свойство, которое должно сохраняться в процессе. Проверяют неизменность баланса после отказа или равенство уменьшения принятой сумме.

### Разобранный пример

Учебный тариф: b = 10000, k = 2, r = 3000. Составьте таблицу тестов для d = 1, 2, 3.

1. d = 1: 10000.
2. d = 2: 10000.
3. d = 3: 10000 + 3000 = 13000.

Ответ: 10000; 10000; 13000

### Практика — `case-tests-practice-1`

Граница k = 4. Какой набор расстояний проверяет её саму и обе стороны?

- a) 1, 2, 3
- b) 5, 6, 7
- c) 3, 4, 5

Ключ: c

1. Возьмите по шагу ниже и выше границы.
2. Добавьте саму границу.

Типичная ошибка: Не используйте только примеры одной ветви.

Подсказка: Три случая: ниже, равно, выше.

- a: Все значения ниже границы.
- b: Все значения выше границы.
- c: Есть случаи ниже, на границе и выше.

### Практика — `case-tests-practice-2`

Тариф: b = 8000, k = 1, r = 2000. Каков ожидаемый ОБЩИЙ выход теста при d = 3?


Ключ: 12000

1. Превышение: 3 − 1 = 2.
2. 8000 + 2 × 2000 = 12000.

Типичная ошибка: Ожидаемый результат теста тоже нужно вычислять независимо.

Подсказка: Добавьте к базе только плату за превышение.


### Входная проверка — `case-tests-precheck`

Запрос отклонён. Какой инвариант проверяется?

- a) Конечный баланс равен исходному
- b) Конечный баланс равен нулю
- c) Баланс каждый раз увеличивается

Ключ: a

1. В ветви отказа нет обновления счёта.
2. Прежний баланс должен сохраниться.

Типичная ошибка: Проверяйте и побочные эффекты в ветви ошибки.

- a: Отказ не изменяет средства.
- b: Отказ не опустошает счёт.
- c: Такое правило не задано.

### Итоговая проверка — `case-tests-postcheck`

В тесте записан только вход, ожидаемого выхода нет. Чего не хватает?

- a) Только фоновой картинки экрана
- b) Больше случайных нажатий кнопок
- c) Явного критерия для сравнения результата

Ключ: c

1. Тестовый вход выполняется.
2. Полученный результат сравнивается с заранее определённым ожидаемым значением.

Типичная ошибка: Для каждого теста записывайте проверяемый результат или свойство.

- a: Картинка не оценивает правильность вычисления.
- b: Больше действий без критерия не решают проблему.
- c: Ожидаемый выход различает правильное и неправильное.
