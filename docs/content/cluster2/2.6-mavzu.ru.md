## Потребность пользователя и цель

Креативное решение начинается с проблемы пользователя. «Необычная» функция сама по себе не означает полезность: объясните, кому, в какой ситуации и как она помогает.

Если студент забывает сроки заданий, напоминание, недельный календарь или список приоритетов могут быть разными решениями. Сравнивайте их по потребности и ограничениям.

Сценарий «студент вводит задачу, задаёт срок, видит ближайшую задачу» уточняет функцию. Запрашивайте персональные данные только при необходимости.

### Разобранный пример

Студент забывает сроки домашних заданий. Постройте минимальный полезный сценарий.

1. Потребность — знать ближайший срок.
2. Вводятся название задачи и срок.
3. Показывается список ближайших задач.

Ответ: Ввод → срок → ближайшие задачи

### Практика — `design-needs-practice-1`

Потребность: студент забывает срок. Какая функция помогает непосредственно?

- a) Показ ближайших задач по сроку
- b) Случайная смена фона при каждом нажатии
- c) Скрыть название задачи

Ключ: a

1. Свяжите функцию с проблемой.
2. Показ сроков соответствует потребности.

Типичная ошибка: Не отождествляйте новизну и полезность.

Подсказка: Какой вариант уменьшает ошибку пользователя?

- a: Это показывает именно нужную информацию.
- b: Это не решает проблему сроков.
- c: Это затрудняет распознавание нужной задачи.

### Практика — `design-needs-practice-2`

Какие данные нужнее всего для простого списка задач?

- a) Номер паспорта и банковской карты
- b) Только любимый цвет пользователя
- c) Название задачи и состояние выполнения

Ключ: c

1. Проверьте цель каждого поля.
2. Названия и состояния достаточно для основного списка.

Типичная ошибка: Не собирайте ненужные данные.

Подсказка: Что именно нужно для работы функции?

- a: Эти данные не нужны для этой задачи.
- b: Этого недостаточно для учёта задач.
- c: Они обеспечивают основную функцию списка.

### Входная проверка — `design-needs-precheck`

Какая запись уточняет требование «пусть приложение будет современным»?

- a) Пусть будут все функции сразу
- b) Студент может ввести новую задачу и увидеть подтверждение сохранения
- c) Пусть будет очень крутым и уникальным

Ключ: b

1. Превратите абстрактное качество в сценарий.
2. Действие и ожидаемый результат можно проверить.

Типичная ошибка: Не опирайтесь на непроверяемые оценочные слова.

- a: Неопределённы объём и критерий приёмки.
- b: Есть проверяемое действие и результат.
- c: Нет измеримого поведения.

### Итоговая проверка — `design-needs-postcheck`

Требуется работа без интернета. Какая идея соответствует ограничению?

- a) Хранить задачи на устройстве и показывать их позже
- b) При каждом открытии обязательно ждать ответ сервера
- c) Удалять все задачи при отсутствии интернета

Ключ: a

1. Ограничение требует основной работы без сети.
2. Локальное хранение может обеспечить этот сценарий.

Типичная ошибка: Интересная идея не должна нарушать обязательное ограничение.

- a: Основной сценарий выполняется без сети.
- b: Без сети основной поток останавливается.
- c: Это теряет данные пользователя.

## Функции и минимальный объём

Разделите мини-приложение на задачи: получение, проверка, сохранение и показ данных. У каждой части должна быть одна ясная ответственность.

Минимальная рабочая версия выполняет один важный сценарий пользователя до конца. Прежде ненужной статистики или украшений завершите основное сохранение и повторный показ.

Поток данных: INPUT title → VALIDATE title → SAVE task → SHOW list. Если проверка нашла ошибку, перехода к SAVE нет.

### Разобранный пример

Задача с пустым названием не должна сохраняться. Запишите правильный поток.

1. Получается введённое название.
2. Проверяется пустота; при ней сообщение и возврат.
3. Если допустимо, сохранение и обновлённый список.

Ответ: Получить → проверить → сохранить → показать

### Практика — `design-functions-practice-1`

Что удобно возвращать части, которая только проверяет данные?

- a) Скрыто отправлять заказ самостоятельно
- b) Удалять все задачи
- c) Результат допустимости или необходимости исправления

Ключ: c

1. Проверяющая часть оценивает данные.
2. Управляющая часть использует результат для следующего действия.

Типичная ошибка: Не собирайте в одной части несвязанные задачи.

Подсказка: Название части должно соответствовать её действительной задаче.

- a: Это побочный эффект вне проверки.
- b: Проверка не требует такого удаления.
- c: Ответственность проверки остаётся ясной.

### Практика — `design-functions-practice-2`

Каков первый полный поток минимального приложения задач?

- a) Статистическая панель без вычислений
- b) Добавить задачу → увидеть в списке → отметить выполненной
- c) Только анимация фона

Ключ: b

1. Минимальный не означает только внешний вид.
2. Выполняется основной жизненный цикл задачи.

Типичная ошибка: Не подменяйте основную функцию украшением.

Подсказка: Может ли пользователь выполнить задачу от начала до конца?

- a: Это не работающий основной поток.
- b: Один полезный сценарий работает до конца.
- c: Нет основной работы с данными.

### Входная проверка — `design-functions-precheck`

Название пустое. Какой поток соответствует требованию?

- a) VALIDATE → ERROR → INPUT
- b) SAVE → VALIDATE → SHOW
- c) SAVE → SUCCESS

Ключ: a

1. Пустое название недопустимо.
2. Происходит возврат к вводу без сохранения.

Типичная ошибка: Проверка должна работать до сохранения.

- a: Предоставляется исправление без сохранения.
- b: Недопустимая задача уже сохранена.
- c: Проверка полностью пропущена.

### Итоговая проверка — `design-functions-postcheck`

В списке 4 задачи. Одна новая допустимая задача сохраняется, следующий запрос с пустым названием отклоняется. Сколько задач в конце?


Ключ: 5

1. Допустимое сохранение увеличивает число с 4 до 5.
2. Отклонённый ввод не создаёт новой задачи.

Типичная ошибка: Не считайте отклонённую попытку сохранённым объектом.


## Состояния интерфейса и обратная связь

Интерфейс должен различать исходное состояние, загрузку, успех, пустоту и ошибку. Пустой список не ошибка: задач ещё может не быть.

Не говорите «сохранено», пока сохранение не завершилось. Блокировка кнопки уменьшает повторные нажатия; отсутствие дублей обеспечивается и в части сохранения данных.

Не обозначайте ошибку только цветом: покажите понятный текст и способ исправления. Добавьте в сценарий использование клавиатуры и перемещение фокуса.

### Разобранный пример

Запрос сохранения выполняется, затем приходит ошибка. Какова последовательность состояний?

1. Сначала состояние SAVING.
2. После ошибки — ERROR и исправление/повтор.
3. SUCCESS не показывается, потому что успех не подтверждён.

Ответ: SAVING → ERROR

### Практика — `design-states-practice-1`

Запрос ещё не завершён. Какое сообщение правильно?

- a) Данные полностью потеряны
- b) Сохранение…
- c) Успешно сохранено

Ключ: b

1. Результат процесса пока неизвестен.
2. Покажите состояние загрузки.

Типичная ошибка: Не показывайте ожидаемый результат как завершившийся факт.

Подсказка: Какое состояние подтверждено сейчас?

- a: Для такого вывода нет данных.
- b: Отражено реальное промежуточное состояние.
- c: Успех ещё не подтверждён.

### Практика — `design-states-practice-2`

Ошибка отмечена только красной рамкой. Какое дополнение полезно?

- a) Понятный текст ошибки и исправления рядом с полем
- b) Скрыть текст красным цветом
- c) Молча закрыть ошибку

Ключ: a

1. Один цвет не передаёт достаточного смысла.
2. Текст указывает ошибку и следующий шаг.

Типичная ошибка: Не используйте изменение вида вместо объяснения.

Подсказка: Сообщение должно быть понятно и без различения цвета.

- a: Смысл не зависит только от цвета.
- b: Объяснение исчезает.
- c: Пользователь не понимает, что произошло.

### Входная проверка — `design-states-precheck`

Список успешно загружен, но задач нет. Какое это состояние?

- a) Показать как ошибку сервера
- b) Бесконечная загрузка
- c) Пустое состояние с предложением добавить задачу

Ключ: c

1. Отметьте завершение загрузки.
2. Пустой результат — отдельное понятное состояние.

Типичная ошибка: Не путайте пустой результат и техническую ошибку.

- a: Оснований для этого нет.
- b: Запрос уже завершён.
- c: Запрос успешен, а данные пусты.

### Итоговая проверка — `design-states-postcheck`

Сохранение вернуло ошибку. Какой переход состояний подходит?

- a) SAVING → удаление всех данных
- b) SAVING → ERROR, ввод сохранён и предложен повтор
- c) SAVING → SUCCESS, ошибка скрывается

Ключ: b

1. Ошибочный результат выбирает ERROR.
2. Работа пользователя сохраняется, предоставляется повтор.

Типичная ошибка: Не показывайте неуспешный запрос как готовый результат.

- a: Такой побочный эффект не требовался.
- b: Ошибка показывается без потери введённой работы.
- c: Это ложно подтверждает результат.

## Сравнение идей по критериям

Запишите несколько идей для одной потребности, затем сравните по полезности, сложности реализации и ограничениям. Первая записанная идея не становится победителем автоматически.

Таблица оценки делает выбор прозрачным, но баллы зависят от критериев и весов. Например, обязательную работу без интернета нельзя обойти суммой баллов.

Закрытые вопросы проверяют решение по заданному критерию. Они не оценивают уникальность свободного творческого продукта или общую креативность человека.

### Разобранный пример

Идея A: полезность 4, простота 3. B: полезность 3, простота 5. Веса равны, большая сумма предпочтительнее. Что выбрать?

1. A всего: 4 + 3 = 7.
2. B всего: 3 + 5 = 8.
3. По заданному критерию выигрывает B.

Ответ: B

### Практика — `design-alternatives-practice-1`

Для идеи полезность 5, простота 3. Оценка = 2 × полезность + простота. Какова оценка?


Ключ: 13

1. С весом полезности: 2 × 5 = 10.
2. 10 + 3 = 13.

Типичная ошибка: Не применяйте вес одинаково ко всем критериям.

Подсказка: Отдельно проверьте коэффициент каждого критерия.


### Практика — `design-alternatives-practice-2`

Обязательное требование: работа без интернета. У A балл выше, но нужна сеть. У B ниже, но требование выполнено. Каково решение?

- a) Выбрать A только за большую сумму
- b) Скрыть требование от пользователя
- c) Выбрать соответствующий B или переработать A

Ключ: c

1. Сначала исключаются несоответствующие варианты.
2. Затем допустимые сравниваются по баллам.

Типичная ошибка: Различайте баллы критериев и обязательное требование.

Подсказка: Работает ли основной сценарий без выполнения этого требования?

- a: Балл не отменяет обязательное ограничение.
- b: Это нарушает согласованное условие.
- c: Обязательное требование имеет приоритет.

### Входная проверка — `design-alternatives-precheck`

Две идеи равны по всем заданным критериям. Какой вывод обоснован?

- a) Обе совершенно бесполезны
- b) Нужен дополнительный критерий или небольшой пользовательский тест
- c) Первая идея научно превосходит другую

Ключ: b

1. Заданные критерии не показали различия.
2. Выбор уточняется новыми данными.

Типичная ошибка: Не выводите вымышленного победителя из равенства.

- a: Равенство не означает бесполезности.
- b: Текущая таблица не даёт единственного выбора.
- c: Порядок не является доказательством превосходства.

### Итоговая проверка — `design-alternatives-postcheck`

A: полезность 4, простота 2. B: полезность 3, простота 5. Оценка = 2 × полезность + простота. На сколько оценка B больше A?


Ключ: 1

1. A = 2 × 4 + 2 = 10.
2. B = 2 × 3 + 5 = 11; разность 1.

Типичная ошибка: Возвращайте запрошенную разность, а не общий балл.


## Прототип и план проверки

Прототип — простейший образец для проверки идеи: бумажные экраны, кликабельный макет или небольшая работающая часть. Заранее записывается проверяемое предположение.

В тесте дайте пользователю задачу, например добавить новую задачу и отметить выполненной. Наблюдайте остановки, ошибки и понимание результата; не подсказывайте заранее все нажатия.

После наблюдения выберите одну проблему, измените решение и проверьте снова. В открытых мини-проектах используются критерии самопроверки; самопроверка не заменяет результат автоматической проверки платформы.

### Разобранный пример

Пользователь не нашёл кнопку сохранения. Каков следующий небольшой эксперимент?

1. Наблюдение: кнопка не находится.
2. Уточните подпись и расположение.
3. Повторите тест с той же задачей.

Ответ: Наблюдение → изменение → повторная проверка

### Практика — `design-prototype-practice-1`

Цель теста: проверить понятность добавления задачи. Какое задание подходит?

- a) Нажмите все кнопки, которые я назову
- b) Назовите только цвет экрана
- c) Добавьте завтрашнее задание в список

Ключ: c

1. Задание направлено на выполнение цели.
2. Наблюдайте, не указывая заранее последовательность нажатий.

Типичная ошибка: Не превращайте тест самостоятельного использования в выполнение инструкции.

Подсказка: Тест должен показывать, что пользователь находит самостоятельно.

- a: Подсказка скрывает трудность самостоятельного поиска.
- b: Поток добавления не проверяется.
- c: Это выполняет реальный пользовательский сценарий.

### Практика — `design-prototype-practice-2`

Один пользователь не нашёл кнопку. Какой вывод осторожен и полезен?

- a) Обвинить пользователя и прекратить тест
- b) Возможна проблема обнаружения кнопки; нужно изменить и проверить снова
- c) Никто не может пользоваться этим приложением

Ключ: b

1. Проблема наблюдалась в конкретном сценарии.
2. Проверьте предположение небольшим изменением и повторным тестом.

Типичная ошибка: Не делайте вывод обо всех пользователях из малого наблюдения.

Подсказка: Разделяйте наблюдение и обобщение.

- a: Это не использует данные для улучшения дизайна.
- b: Наблюдение указывает на проблему, но не даёт всеобщего вывода.
- c: Одно наблюдение не даёт такого общего вывода.

### Входная проверка — `design-prototype-precheck`

Что хорошо проверяет бумажный прототип?

- a) Порядок экранов и понятность подписей
- b) Точную скорость сервера в секундах
- c) Параллельные транзакции базы данных

Ключ: a

1. Определите слой, который способен проверить прототип.
2. Бумажные экраны проверяют поток и текст.

Типичная ошибка: Не считайте доказанным свойство вне возможностей типа прототипа.

- a: Для этого не нужен реальный сервер.
- b: На бумаге сервер не выполняется.
- c: Это требует проверки работающей системы.

### Итоговая проверка — `design-prototype-postcheck`

Подпись кнопки изменена. Как проверить улучшение?

- a) Достаточно, что автору красиво
- b) Удалить все остальные функции
- c) Повторить ту же задачу и наблюдать поиск и ошибки

Ключ: c

1. Проверяйте изменение одной проблемы.
2. Сравните с новым наблюдением в том же сценарии.

Типичная ошибка: Само изменение не доказывает пользу.

- a: Это не проверяет понимание пользователя.
- b: Это не выделяет эффект одной подписи.
- c: Получаются данные, связанные с прежней проблемой.


## Мини-проект: учебный планировщик без интернета

Студент добавляет задачу с названием и сроком, отмечает выполнение и находит ближайшие сроки. Основной сценарий должен работать без интернета. Подготовьте бумажный прототип или мини-приложение.

### Ограничения

- Название задачи не должно быть пустым; конфиденциальные персональные данные не запрашиваются.
- При ошибке введённый текст сохраняется; неподтверждённое сохранение не показывается как успех.
- Бумажный прототип не доказывает скорость сохранения; в работающем приложении локальное хранение проверяется повторным открытием.

### Этапы

- Сначала постройте блок-схему ввода → проверки → сохранения → показа задачи.
- Опишите варианты списка, календаря и карточек приоритетов; сравните по потребности и работе без сети.
- Нарисуйте экраны пустоты, ввода, сохранения, ошибки и успеха выбранного варианта.
- Проверьте поток: добавление, отметка выполнения, отклонение пустого названия.
- Запишите одно пользовательское наблюдение, внесите одно изменение и повторите ту же задачу.

### Материалы результата

- Цель и контракт входа/выхода; краткое сравнение трёх вариантов.
- Блок-схема, экраны или небольшой работающий образец.
- Таблица тестов: вход, ожидаемый и наблюдаемый результат; запись до/после изменения.

### Самопроверка

- Объяснена ли связь потребности и функции?
- Работают ли основной поток и ошибка без потери данных или ясно показаны в прототипе?
- Обоснован ли выбор варианта критериями?
- Записан ли ожидаемый результат для границ и пустого входа?
- Есть ли изменение по наблюдению и повторная проверка?


## Мини-проект: помощник очереди в библиотеке

Создайте прототип электронной очереди обслуживания библиотеки. Новый студент добавляется в конец, вызов берёт из начала. Вызов из пустой очереди не создаёт человека. Используйте анонимные номера вместо имён.

### Ограничения

- Первый пришедший вызывается первым; приоритетов в этой модели нет.
- Различайте пустую очередь и техническую ошибку.
- Каждое подтверждённое добавление создаёт ровно один номер; повтор нажатия не должен стирать неподтверждённый результат.

### Этапы

- Выделите части добавления, вызова и показа списка.
- Сравните список последовательных номеров, карточки очереди и окно только следующего номера.
- Запишите небольшой псевдокод: при пустоте EMPTY, иначе вернуть и удалить начало.
- Проверьте добавление двух человек, вызов одного, просмотр оставшегося и пустую очередь.
- Проверьте подписи экрана с пользователем и обоснуйте одно изменение.

### Материалы результата

- Правило очереди, диаграмма состояний и хотя бы краткие эскизы двух интерфейсов.
- Таблица трассировки с очередью до/после каждого действия.
- Выбор решения, результаты тестов и запись следующего улучшения.

### Самопроверка

- Сохраняется ли порядок очереди во всех показанных действиях?
- Понятно ли показана пользователю пустая очередь?
- Сравнены ли хотя бы два решения по одному критерию?
- Раздельно ли записаны вход и ожидаемое состояние теста?
- Удовлетворена ли потребность без персональных данных?
