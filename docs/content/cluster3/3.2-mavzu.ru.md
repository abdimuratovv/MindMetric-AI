## Задачи и контракты модулей

Результат: Распределяете работу с ответственным, входом, выходом и критерием приёмки.

Модуль даёт отдельный полезный результат: каталог находит сведения о книге, модуль выдачи выдаёт доступный экземпляр. Вместе с названием задачи записывают ответственного, зависимости и критерий завершения.

В контракте согласуют параметры, результат и ошибочные случаи. Например, find_book(book_id) возвращает None, если книга не найдена. Если один возвращает None, а другой ждёт {}, совместная работа нарушится даже при отдельных успехах.

«Готово» означает не только написанный код: прошли тесты контракта, есть пояснение и ревью коллеги. Раннее сообщение о препятствии и запись нового соглашения экономят время команды.

### Разобранный пример

Автор каталога возвращает None из find_book(id), если книга не найдена. Модуль выдачи читает title из результата. Что согласовать до интеграции?

1. Запишите случаи найдено и не найдено.
2. Договоритесь отклонять выдачу при None.
3. Составьте общие тесты обоих случаев.

Ответ: Единый контракт и интеграционный тест.

## Парное программирование

Результат: Объясняете роли драйвера и навигатора и полезную смену ролей.

Драйвер пишет код за клавиатурой и объясняет намерение. Навигатор следит за требованием, следующим шагом, тестами и рисками. Оба думают активно; навигатор не зритель.

Меняйте роли после небольшой задачи или через согласованный короткий интервал. Перед сменой передайте состояние, следующий тест и открытый вопрос. Быстро печатающий участник не должен всегда оставаться драйвером.

При разногласии вернитесь к требованию и небольшому тесту. Вместо «ты неправ» спросите «что будет при пустом входе?» — это помогает проверить проблему.

### Разобранный пример

Драйвер пишет функцию выдачи. Навигатор спрашивает, можно ли снова выдать возвращённую книгу. Соответствует ли это роли?

1. Навигатор проверяет требования и состояния.
2. Добавляется тест состояния после возврата.
3. Решение принимается по результату.

Ответ: Да, это полезный вопрос по требованию и тесту.

- c) Не слушая драйвера, писать другой модуль

Подсказка: Какая мыслительная работа нужна помимо клавиатуры?

Ключ: a

1. Одна задача выполняется совместно.
2. Навигатор следит за требованиями и тестами.

Типичная ошибка: Навигатор не пассивный наблюдатель.

- a: Это содержательное сопровождение написания кода.
- b: Активная роль в паре не выполняется.
- c: Разделяет общее внимание пары.

- a: Контекст может потеряться.

- c: Новый драйвер продолжит с пониманием.

- a) Запретить тесты
- b) Сравнить варианты небольшим тестом по требованию

## Состояния файлов и коммит

Результат: Различаете рабочее дерево, индекс и коммит.

Рабочее дерево — текущие файлы. git add помещает выбранное содержимое в индекс. git commit записывает состояние индекса в локальную историю. Для передачи коммита на удалённый сервер нужен отдельный push.

git status показывает состояние. git diff обычно сравнивает рабочее дерево с индексом, git diff --staged — индекс с HEAD. Новая правка после add не попадает в индекс автоматически.

Небольшой осмысленный коммит объясняет одну задачу или исправление. Перед коммитом проверьте diff и тесты. Даже в учебных упражнениях не включайте пароли и токены.

### Разобранный пример

Отслеживаемый note.txt был v1. Вы изменили на v2, выполнили git add note.txt, затем изменили на v3. Что сохранит коммит?

1. При add в индекс попало v2.
2. Позднее v3 осталось в рабочем дереве.
3. Обычный git commit сохранит v2 из индекса.

Ответ: В коммите v2; в рабочем файле остаётся v3.

### Практика — `git-staging-practice-1`

Что берёт обычный git commit после git add file.py?

- a) Всегда все файлы на всех дисках
- b) Только файлы на сервере
- c) Выбранное содержимое индекса

Подсказка: Что подготавливает add?

Ключ: c

1. Add готовит индекс.
2. Commit записывает это состояние.

Типичная ошибка: Рабочее дерево и индекс не всегда совпадают.

- a: Git работает в рамках репозитория и индекса.
- b: Локальный коммит не берётся с сервера.
- c: Коммит записывает состояние индекса.

### Практика — `git-staging-practice-2`

- a) git log --oneline
- b) git diff --staged
- c) Только git diff

Подсказка: Какой параметр показывает индекс?

Ключ: b

1. Источник коммита — индекс.
2. Посмотрите его diff.

Типичная ошибка: Различайте историю и готовящиеся изменения.

- a: Показывает прежнюю историю.
- b: Сравнивает индекс с HEAD.
- c: Обычно показывает неиндексированные изменения.

### Входная — `git-staging-precheck`

### Итоговая — `git-staging-postcheck`

Отслеживаемый a.txt был v1. Изменили на v2 и add, затем на v3 и снова add. Содержимое обычного коммита?

- c: Второй add обновил индекс.

## Ветка, ревью и слияние

Результат: Выбираете процесс проверки и слияния небольшого изменения из отдельной ветки.

Ветка даёт отдельную линию работы. Учебный процесс: ветка от согласованной базы, небольшая правка, тест, коммит, ревью, затем merge в целевую ветку. Pull request — средство ревью на хостинге, а не сама локальная система Git.

git merge feature объединяет историю feature с текущей веткой. Сначала проверьте текущую ветку. Слияние без конфликтов не гарантирует смысловую правильность: результат проверяют тестами и контрактом.

Для ревью описывают, что изменилось, почему и как проверено. Замечания коллеги перепроверяют; новая правка после одобрения тоже проходит нужное ревью и тест.

### Разобранный пример

Текущая ветка main, рабочее дерево чистое. В feature прошёл тест каталога. Какую ветку обновляет git merge feature?

1. Убедитесь, что текущая ветка main.
2. Merge включает feature в main.
3. Повторите тест объединённого состояния.

Ответ: Обновляется main; интеграционный тест всё равно нужен.

- b) Текущая ветка, diff и результат тестов
- c) Только прочитать сообщение коммита без diff и тестов

Подсказка: На какую ветку влияет merge?

Ключ: b

1. Определите целевую ветку.
2. Проверьте изменение и его проверку.

Типичная ошибка: Не выполняйте merge без контекста.

- a: Даже правильный код можно слить не в ту ветку.
- b: Известно, куда и что добавляется.
- c: Описание не гарантирует фактическое изменение и правильность.

## Конфликт и общий результат

Результат: Решаете конфликт по требованию и готовите доказательства интеграции и защиты.

При несовместимых изменениях одного места Git может показать конфликт. Маркеры <<<<<<<, ======= и >>>>>>> не являются итоговым кодом. Прочитайте намерения обеих сторон и запишите итог по требованию.

Слепой выбор одной стороны может потерять другое требование. После удаления маркеров проверяют синтаксис, контракт и общий поток; разрешённый файл добавляют в индекс и завершают merge.

На защите каждый объясняет свой модуль, интерфейс, один ошибочный случай и роль в общем результате. Вместе с демо показывают тесты; число коммитов не является оценкой способности человека к сотрудничеству.

### Разобранный пример

Одна ветка изменила лимит на 3, другая на 5. Согласованное требование: не более 4 книг на читателя. Решение конфликта?

1. Оба варианта не соответствуют требованию.
2. Установите лимит 4 и удалите маркеры.
3. Проверьте случаи 3, 4 и 5 книг по требованию.

Ответ: Нужен третий вариант, соответствующий соглашению.

Подсказка: Какое требование нужно сохранить?

Ключ: a

1. Определите намерение каждой стороны.
2. Запишите единое подходящее решение.

Типичная ошибка: Не связывайте выбор с расположением фрагмента.

- a: Итоговый код выбирается по смыслу.
- b: Он может потерять другое требование.
- c: Могут остаться повторы или противоречия.

Ключ: c

Типичная ошибка: Чистый текст не гарантирует правильного смысла.

- a: Тесты и состояние индекса не проверены.
- b: Исчезает критерий правильности.

### Входная — `git-conflict-precheck`

- a) Показать только пройденный отдельный тест
- b) Вход/выход и переход состояния на границе модулей
- c) Повторить только внутренний тест отдельного модуля

Ключ: b

1. Проверьте соединение модулей.
2. Повторите вход общего теста.

Типичная ошибка: Отдельный успех не равен общему.

- a: Общий сбой останется.
- b: Там может находиться причина сбоя интеграции.
- c: Он может не покрывать контракт между модулями.

### Итоговая — `git-conflict-postcheck`

- a) Каждый объясняет интерфейс, общий поток и ошибочный случай показываются тестом
- b) Говорит только автор большинства коммитов
- c) Только снимок главного экрана

2. Каждый объясняет границу своего модуля.
