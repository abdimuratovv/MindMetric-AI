# Командный мини-проект библиотеки

Копия преподавателя — с решениями

[README](README.md)

## Цель

Применить контракт модулей, Git, ревью и интеграцию в группе из 2–3 человек.

## Материалы

- Python 3, Git и отдельный новый локальный репозиторий; реальные данные учащихся и читателей не нужны. Remote необязателен.

- Начальный catalog = {"b1": {"title": "Algorithms", "total": 1, "available": 1}}; loans = {}. Ключ loans — (reader, book_id), значение — положительное целое количество.

## Контракт

- find_book(catalog, book_id) возвращает новый dict или None; исходный catalog не меняется. borrow(catalog, loans, reader, book_id): ok, not_found или unavailable. return_book с теми же параметрами: ok, not_found или no_loan.

- Предусловия: reader и book_id — непустой текст; catalog согласован, total и available — неотрицательные целые; available <= total; текущие займы согласованы с учётом. Параллельность, база хранения и аутентификация не входят в упражнение.

- Успешная выдача уменьшает available на 1 и увеличивает долг на 1. Возврат выполняется только при долге этого reader. При отказе catalog и loans не меняются; ключ нулевого долга удаляется.

- Для каждой книги available + сумма долгов всех reader = total. Инвариант сохраняется после каждой успешной операции.

## Этапы

1. Роли: каталог и интерфейс; выдача/возврат; интеграция/тесты. При 2 участниках интеграция общая. Меняйте драйвера/навигатора, каждый делает ревью другого модуля.

2. В CONTRACT.md запишите сигнатуры, коды ответа и отказы. Для каждой задачи назначьте ответственного и приёмочный тест. Сначала проверьте соединение небольшими заглушками по контракту.

3. Работайте в отдельных ветках и небольших коммитах. Просматривайте git status, git diff и git diff --staged. До слияния нужны ревью коллеги и тест.

4. Симуляция конфликта: в чистой базе запишите display_limit=2 в POLICY.md и закоммитьте. review-a и review-b создайте от одной базы. В одной замените на 3, в другой на 5. Слейте в main сначала одну, затем другую; разрешите конфликт по итоговому соглашению display_limit=4. Это лимит отображения, а не ограничение выдачи.

5. Общий поток: найти b1 → выдать r1 → отклонить повторную выдачу r2 → возврат r1 → выдать r2. Проверьте также отсутствующую книгу и возврат без долга.

6. Каждый объясняет свой модуль, связь с другим, один ошибочный случай и одно решение ревью.

## Результат работы

- Код; CONTRACT.md; таблица задач/ролей; небольшой Git log и подтверждение diff; запись решения конфликта; результаты общих тестов; краткая защита. Не ранжируйте участников по числу коммитов.

## Рубрика

- Контракт: 0 — нет; 1 — частично; 2 — согласованы сигнатуры, коды и предусловия.

- Интеграция: 0 — общего потока нет; 1 — только обычный путь; 2 — проверены общий путь, отказ и инвариант.

- Подтверждение сотрудничества: 0 — нет; 1 — задачи разделены без ревью; 2 — есть смена ролей и обоснованное взаимное ревью.

- Git и защита: 0 — следов нет; 1 — не хватает коммита или объяснения; 2 — есть содержательный diff, причина конфликта и объяснение каждого. До 8 баллов — рубрика проекта.

## Решение преподавателя

- library_reference.py — работающий образец преподавателя; это не архитектура реальной многопользовательской системы.

- Выдача b1/r1: ok, available=0, loans[("r1", "b1")]=1. Запрос r2 — unavailable, оба состояния неизменны. Возврат r1 — ok, available=1, ключ долга удаляется. Затем выдача r2 — ok.

- Для отсутствующей книги — not_found; возврат reader без своего долга — no_loan. В обоих случаях состояние сохраняется точно. Проверяется, что правка результата find_book не меняет исходный каталог.

- Итог конфликта — display_limit=4. Почему не 3 или 5, объясняется соглашением. На защите уточните, почему успех merge не заменяет общий тест.
