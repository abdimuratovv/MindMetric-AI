## Различение видов ошибок

Результат: По признакам различаете синтаксическую ошибку, ошибку выполнения и логическую ошибку.

Python сначала разбирает код. Например, пропуск двоеточия в заголовке if вызывает SyntaxError; обычное выполнение не начинается. Место из сообщения не всегда является причиной: проверьте и предыдущую строку.

Синтаксически правильный код может остановиться во время выполнения: 8 / 0 даёт ZeroDivisionError. Если код завершился, но результат противоречит требованию, возможна логическая ошибка. Для проверки нужен ожидаемый результат.

До исправления запишите вид ошибки, вход и требование. Устранение первой ошибки не гарантирует отсутствия следующих.

### Разобранный пример

Python 3, намеренно ошибочный код:
```python
if 4 > 2
    print(4)
```
Почему нет результата?

1. Проверьте заголовок if.
2. В конце нет :.
3. Исправьте синтаксис и проверьте снова.

Ответ: SyntaxError; заголовок должен быть if 4 > 2:.

- b: Успешное выполнение не заменяет требование.
- c: Площадь равна 15, формула относится к другой величине.

## Воспроизведение ошибки

Результат: Составляете воспроизводимый отчёт и небольшой контрпример.

Хороший отчёт содержит версию, точный вход, шаг запуска, ожидаемый и фактический результат. «Не работает» недостаточно для поиска причины. Вместо секретных данных используйте небольшой искусственный вход.

Минимальный пример сохраняет ошибку, убирая лишние части. Если ошибка исчезла, отмените это сокращение. Минимальность — не просто наименьшее число строк: данных должно хватать для проверки причины.

Гипотеза — проверяемое предположение: «сбой возникает только на пустом списке». Сделайте одно изменение и повторите тот же тест; несколько одновременных правок скрывают причину.

### Разобранный пример

Функция mean(xs) возвращает sum(xs) / len(xs). Для [2, 4] получается 3, для [] — ZeroDivisionError. Сократите отчёт.

1. Оставьте Python 3 и функцию mean.
2. Используйте вход [].
3. Уточните требование для пустого списка; запишите ошибку и ожидаемый результат.

Ответ: Пустой вход воспроизводит сбой; нужен контракт для пустого случая.

Ключ: b

Типичная ошибка: Не ограничивайте отчёт оценочным суждением.

- a: Сообщение полезно, но недостаточно для воспроизведения и проверки расчёта.
- b: Есть точное расхождение и способ повторения.

- b: Переписывание не является проверяемой гипотезой о причине.

- b: Можно связать результат с причиной.
- c: Для этого нет доказательств.

## Трассировка значений и traceback

Результат: Читаете изменения значений по строкам и цепочку ошибки.

В таблице трассировки записывают выполненную строку и значения ПОСЛЕ неё. Проверка условия сама по себе не меняет значение. Отслеживайте, где имя определено и обновлено.

Последняя строка traceback сообщает тип исключения и сообщение. Кадры выше показывают путь вызовов. Найдите проблемное выражение в нижнем относящемся к делу кадре; проверьте и значение от вызывающего кода.

Вместо случайных print наблюдайте состояние до и после подозрительной операции. Наблюдение не должно менять переменную; не выводите секретные данные в диагностические записи.

### Разобранный пример

Python 3:
```python
x = 2
x = x + 3
y = x * 2
```
Найдите y трассировкой.

1. После первой строки x=2.
2. После второй x=5.
3. На третьей y=10.

Ответ: 10

### Практика — `debug-trace-practice-1`

Python 3: x = 4; x = x + 2; x = x * 3. Конечное x?


Подсказка: Запишите x после каждой строки.

Ключ: 18

1. Сначала x=6.
2. Затем 6 × 3 = 18.

Типичная ошибка: Следующая строка берёт обновлённое x.


### Практика — `debug-trace-practice-2`

- a) Только переименовать файл
- b) Всегда удалять последний print
- c) Как делитель указанного выражения стал 0

Подсказка: Какой операнд может быть нулём?

Ключ: c

1. Прочитайте тип сообщения.
2. Найдите делитель и источник его значения.

Типичная ошибка: Изменение текста сообщения не устраняет причину.

- a: Значение делителя не изменится.
- b: Это не проверяет причину сообщения.
- c: Это прямо связано со смыслом исключения.

### Входная — `debug-trace-precheck`

Python 3: a = 3; b = a; a = 8; print(b). Что выводится?


Ключ: 3

1. b получает тогдашнее значение 3.
2. Присваивание a значения 8 не меняет b.

Типичная ошибка: Не считайте присваивание целого постоянной связью формулы.


### Итоговая — `debug-trace-postcheck`

    s = s + x

Ключ: 8

2. Конечное значение 8.

## Точка останова и пошаговая проверка

Результат: Выбираете место остановки и команды step/next/continue по цели.

Точка останова приостанавливает выполнение для проверки состояния; она не исправляет код автоматически. В этом курсе строка паузы со стрелкой считается ещё не выполненной.

В Python pdb команда p x показывает значение; n (next) выполняет текущую строку и обычно переходит к следующей в том же кадре; s (step) может войти в вызываемую функцию; c (continue) продолжает до следующей остановки.

Сначала запишите прогноз, затем наблюдайте состояние. При подозрении на бесконечный цикл проверяйте значение условия и его обновление. Работайте на учебной копии; подтвердите исправление и обычным запуском.

### Разобранный пример

Python 3: x=4 уже выполнено. Стрелка на x = x + 2, строка ещё не выполнена. Что покажут p x, затем n, затем p x?

1. В паузе x=4.
2. n выполняет сложение.
3. При следующем наблюдении x=6.

Ответ: 4, затем 6

### Практика — `debug-breakpoint-practice-1`

Python pdb: x=7. Стрелка на x = x * 2, строка ещё не выполнена. Что покажет p x?


Подсказка: Стрелка на следующей выполняемой строке.

Ключ: 7

1. Пауза перед операцией.
2. Умножение ещё не выполнено, x=7.

Типичная ошибка: Не считайте строку паузы уже выполненной.

- a) q — quit

Ключ: b

1. Цель — войти в функцию.
2. step соответствует этой цели.

Типичная ошибка: Различайте просмотр и выполнение шага.

- a: Это выход из отладки.
- b: Для входа в вызываемую функцию.
- c: Показывает значение, но не делает шаг внутрь.

### Входная — `debug-breakpoint-precheck`

Поставлена точка останова. Какое утверждение верно?

Ключ: a

2. Правильность результата проверяет тест.

Типичная ошибка: Наличие инструмента не гарантирует правильности.

- a: Остановка нужна для сбора фактов.

### Итоговая — `debug-breakpoint-postcheck`

В pdb нужно продолжить выполнение от текущей строки до следующей точки останова. Какая команда?

## Границы и регрессия

Результат: Выбираете минимальное исправление причины и регрессионный набор.

Граничный тест проверяет место разделения требований: ниже лимита, на нём и выше. Для списков важны пустой, одиночный и множественный случаи. Ожидаемый результат берут из контракта, а не из кода.

Минимальное исправление направлено на причину. Например, для «не менее 18» подходит замена > на >=; разрешение всем пользователям скрывает ошибку.

Регрессионный тест проверяет, что старая ошибка не вернулась. После исправления повторите проблемный тест и ранее проходившие обычные и граничные случаи. Вместо скрытия неудачного теста запишите наблюдение и обновите гипотезу.

### Разобранный пример

Требование: разрешить при age >= 18. Код age > 18. Возраст 18 отклоняется. Исправление и тесты?

1. Замените > на >=.
2. Проверьте: 17 отказ, 18 разрешение, 19 разрешение.
3. Повторите и прежний случай большего возраста.

Ответ: Исправление причины и тесты вокруг границы.

### Практика — `debug-regression-practice-1`

- a) Только 1000
- b) 99, 100, 101
- c) 150, 200, 300

Подсказка: Найдите случаи ниже, на границе и выше.

Ключ: b

1. Требование разделяется на 100.
2. Возьмите соседние целые значения.

Типичная ошибка: Одни большие значения не проверяют границу.

- a: Ошибка равенства может не обнаружиться.
- b: Есть обе стороны границы и сама граница.
- c: Все значения по одну сторону.

- a: Проверяются и новый, и прежние случаи.
- b: Не проверяет правильность результатов.

Ключ: c

2. >= соответствует требованию.

- a: Пройдут и отрицательные значения.

### Итоговая — `debug-regression-postcheck`

После исправления новый тест прошёл, прежний упал. Что делать?

- a) Считать достаточным новый тест

Ключ: b

1. Проверьте ожидаемый результат по требованию.
2. Устраните регрессию и повторите оба теста.

Типичная ошибка: Один успех не заменяет все тесты.

- a: Успех одного случая не отменяет ошибку другого.
- b: Если требование не менялось, прежнее поведение нужно сохранить.
- c: Скрывает проблему.
